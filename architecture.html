Why the delay exists: deposits price at the next attested NAV, killing same-block NAV-sniping. The instant "Sync" path prices against an EIP-712-signed quote from the Consensus signer set instead.

02Curator allocation — how a rebalance actually executes

Curator multisig signs
call(target, value, data) e.g. Aave supply/borrow
meta 3/5 · subvault 3/7
Verifier gate
payload must prove membership: allowlist hash, merkle proof, or bitmask match
fail → revert VerificationFailed
RiskManager gate
subvault limit + asset allowlist + vault limit
share-denominated caps
CallModule executes
subvault holds the position; NAV picked up by next oracle report

Where curation limits become code: onboarding a protocol = adding verifier entries (SET_MERKLE_ROOT_ROLE / ALLOW_CALL_ROLE — admin multisigs, behind timelock). The curator cannot touch anything outside the allowlist; the allowlist-setter is therefore the supreme power in the system. BitmaskVerifier can pin exact calldata bytes (amounts included) — unlike Veda's merkle leaves (address args only), amounts CAN be constrained natively here if configured.

03Oracle report — the NAV heartbeat

Updater submits price
off-chain NAV computation, pushed on-chain

SecurityParams checks
supported asset · timeout elapsed · |Δprice| vs last report
abs + relative deviation bands
handleReport()
queues settle at new price · protocol fee accrues · perf fee vs high-watermark
within normal bandreport takes effect immediately — deposits/redemptions price against it
suspicious bandreport is HELD — a separate ACCEPT_REPORT_ROLE (OracleAccepter) must explicitly acceptReport(). The circuit breaker for depeg/exploit days. Note: after a suspicious report the timeout check is bypassed for the correction.
> max deviationrevert InvalidPrice — the report cannot enter at all

The trust model in one line: the share price is an attested NAV with deviation guards — not an on-chain computation. Compromise of updater alone is bounded by (band × frequency); updater + accepter together is the real tail, which is why they are distinct signer sets.

User requests

the liveness dependency

The honest read: 72h = report cadence + redeemInterval + unwind time. Redemption liveness depends on the curator being able to exit positions — which is why "stress-exit quality" scoring (Kelp review, point 6) is not a nicety. EarnETH holds 7.3% idle against this promise; EarnUSD holds 0.1%.

Attack-surface summary (updated with live on-chain reads, 2026-07-18): (1) allowlist-setters > curators — and with timelock delay = 0, root/config changes can land next-block: the multisig thresholds ARE the whole defense, there is no reaction window; (2) RiskManager caps are set to 2^254 (effectively off) — real exposure control is verifier roots + asset allowlists only; (3) FeeManager is plain Ownable by the 5/8 admin Safe, not timelocked — fees changeable in one tx; (4) oracle collusion tail bounded by ±0.5%/report bands & 20h timeout; (5) both pauser Safes are timelock executors with minDelay=0 — reaction is one multisig signature away, fast but never single-signer; (6) redemption liveness is a curator obligation, not a contract guarantee.
